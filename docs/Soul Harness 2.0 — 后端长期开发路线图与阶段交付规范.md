# 一、项目总体目标

Soul Harness 2.0 的后端建设采用分阶段、可验证、可恢复的工程路线。

核心原则：

1. 先完成基础设施和运行时，再建设对外接口。
2. 先明确架构契约，再进行代码实现。
3. 每个阶段独立提交、独立测试、独立复审。
4. 不以测试通过代替架构正确性审查。
5. 不以 AI 的实施报告代替独立验证。
6. 不提前宣称尚未实现的能力已经可用。
7. 不为了赶进度而绕过已确认的架构决议。
8. 所有持久化、恢复、并发和关闭行为都必须有明确语义及测试证据。

总体路线：

- SH-008E：Daemon Assembly & Lifecycle Integration
- SH-009：对外接口、通信与安全架构
- SH-007B：后端端到端集成验收
- C0–C6：认知执行层建设

以上是长期路线图，不代表所有阶段已经批准实施。每个大阶段都需要独立规划、审查和授权。

# 二、第一阶段：SH-008E — Daemon Assembly & Lifecycle Integration

## 总体目标

将已经实现的 Persistence、Runtime、Recovery、Scheduler 等组件正确装配进 Daemon，形成具有真实生命周期管理能力的后端运行入口。

本阶段重点不是让系统立即执行认知任务，而是确保：

- 启动顺序正确。
- Recovery 失败时能够安全停止。
- Scheduler 不会在 Recovery 未完成时启动。
- 资源释放顺序正确。
- Daemon 的状态报告真实反映实际能力。
- 重启和部分恢复不会造成重复操作或状态损坏。

## E1 — Configuration, Error Codes & State Model

**目标：** 完成 Daemon 配置、错误码及状态模型。

主要任务：

1. 增加任务重试配置。
2. 增加 Recovery 配置。
3. 增加 Scheduler 配置。
4. 增加 Ingress 配置。
5. 完善配置边界、安全整数及必填项验证。
6. 统一配置对象冻结策略。
7. 补充 Daemon 启动错误码。
8. 建立 assembled、started、acceptsInput、dispatchesTasks 等能力状态区分。
9. 核对 Runtime Recovery 与 Scheduler 的实际类型契约。
10. 核对 bootToken 与 BOOT_ID_PATTERN 的兼容性。

重点配置：

| 配置 | 默认值 | 范围 |
|---|---:|---:|
| SOUL_TASK_MAX_ATTEMPTS | 必填 | 1–100 |
| SOUL_TASK_RETRY_BACKOFF_MS | 必填 | 0–86400000 |
| SOUL_RECOVERY_BATCH_SIZE | 200 | 1–500 |
| SOUL_RECOVERY_MAX_ROWS | 10000 | 1–1000000 |
| SOUL_RECOVERY_MAX_PERSONAS | 200 | 1–10000 |
| SOUL_SCHEDULER_MAX_TOTAL | 8 | 1–1024 |
| SOUL_SCHEDULER_PER_UNIT | 1 | 1–64 |
| SOUL_INGRESS_QUEUE_CAPACITY | 256 | 1–1000000 |
| SOUL_INGRESS_BUFFER_TTL_MS | 300000 | 1–86400000 |
| SOUL_INGRESS_PERSONA_CAPACITY | 8 | 1–1024 |

交付标准：

- 所有新配置都纳入 CONFIG_ENV_VARS。
- 默认值与范围纳入 CONFIG_LIMITS。
- 配置对象及嵌套策略对象冻结。
- 必填项缺失、空值、越界、小数、非数字和非安全整数均有测试。
- 旧配置行为保持兼容。
- 不引入 shutdown_timeout 硬关闭语义。
- 不修改 Runtime、Persistence、Contracts 或 Migration。
- 完成后提交并停止，等待独立复审。

**当前状态：待实施。**

## E2 — RECOVERING Assembly

**目标：** 将 Recovery 正确接入 Daemon 启动流程。

主要任务：

1. 建立组件装配入口。
2. 接入 PersonaLifecycle。
3. 执行 normalizeCrashedPersonas。
4. 接入 recoverRuntime。
5. 明确 RECOVERING 阶段的启动状态。
6. Recovery 未完整完成时 fail closed。
7. 不在 Recovery 完成前创建或启动 Scheduler。

必须重点测试：

- 九种 Recovery incomplete 原因。
- Recovery 部分持久化后的重启行为。
- 第二次 Recovery 是否重复增加 attempt。
- 是否错误改变 runId。
- 是否破坏已有事件状态。
- Recovery 抛错后的资源释放行为。

九种 incomplete：

1. row_budget_exceeded
2. scan_query_budget_exceeded
3. persona_budget_exceeded
4. probe_budget_exceeded
5. aborted
6. archive_state_present
7. unexpected_event_status
8. invalid_task_row
9. concurrent_modification

必须区分：

- 可通过扩大预算或消除停止条件继续恢复的情况。
- 必须先修复数据才能恢复的 fail-closed 情况。
- 并发修改导致的条件更新失败。

交付标准：

- Recovery 未完成时不进入 READY。
- Recovery 未完成时不启动 Scheduler。
- 部分提交后再次启动不会破坏持久化状态。
- 对每种 incomplete 原因有可复现测试。
- 异常抛出与 incomplete 状态不得混为一谈。
- 完成后停止等待独立复审。

必须明确的能力边界：

- Scheduler 不会提前启动。

- 状态报告不能夸大系统能力。
- 不注册假 Handler。

- 完成后停止等待独立复审。

## E4 — Shutdown & Resource Lifecycle

**目标：** 完成可靠、幂等的 Daemon 关闭流程。

主要任务：

1. 完善异步资源释放。
2. 处理 Ingress.close。
3. 等待 Scheduler.stop 完成。
4. 关闭 Store。
5. 释放 Instance Lock。
6. 处理启动过程中收到 SIGTERM 的情况。
7. 处理重复 stop 调用。
8. 明确资源释放失败时的行为。

推荐的正常关闭顺序：

Ingress close  
→ await Scheduler.stop  
→ Store.close  
→ Instance Lock release

重要架构限制：

- 不设置强制关闭上界。
- Scheduler.stop 未完成前不得关闭 Store。
- 不允许超时后直接放弃 Scheduler 等待并关闭 Store。
- 不伪造 Handler 取消能力。
- Handler 永不 settle 时，Daemon 可能无限等待。
- 当前 Runtime 不具备可验证的运行期强制取消协议。

**特别注意：**

Store.close 失败时如何处理 Instance Lock，必须先形成独立架构决议。

建议研究 Store 关闭失败时保留 Lock 直至进程退出的 fail-closed 方案，但实施 AI 不得自行决定。

交付标准：

- 正常关闭顺序有测试。
- 重复关闭具有明确行为。
- 启动过程中收到停止信号有测试。
- Store 未关闭时不会提前释放 Lock。
- Store.close 失败时的行为符合批准的决议。
- 不存在未经批准的硬超时机制。
- 完成后停止等待独立复审。

# 五、第四阶段：认知执行层 C0–C6

当前 Runtime 的 Scheduler 已经具备任务调度基础，但仍存在重要限制：

- Handler 不支持真正运行期取消。
- Handler 可能永不 settle。
- 同步 CPU Handler 可能阻塞事件循环。
- Scheduler stop 可能无限等待。
- 当前 Daemon 使用固定空 Handler Map，不能派发认知任务。

因此不能直接把模型调用塞进现有空 Handler Map。

必须先设计完整执行架构。

# 八、统一工程推进纪律

以下规则适用于所有阶段。

1. 每次只授权一个实施阶段。
2. 实施完成后立即停止。
3. 不允许自动开始下一阶段。
4. 不允许未经批准修改其他阶段的文件。
5. 不允许擅自修改 Runtime、Persistence、Contracts 或 Migration 来绕过当前问题。
6. 不允许为了测试方便新增生产环境专用 API。
7. 不允许用 mock 测试代替必须进行的真实进程测试。
8. 不允许用静态状态或日志伪造实际运行能力。
9. 不允许擅自改变已经确认的架构决议。
10. 如果遇到任务书前提与实际代码不一致，必须停止并报告。
11. 如果发现需要扩大范围，必须先提出变更建议并等待批准。
12. 每次提交都必须核对父提交、远端状态和实际 Diff。
13. 不允许多个 AI 同时修改同一批生产代码。
14. 独立审计可以并行，但必须保持只读。
15. 不得将未来规划描述为已实现功能。

## 停止条件

遇到以下情况必须停止实施：

- 任务书前提与实际源码不符。
- 现有契约无法满足设计要求。
- 需要修改未经授权的模块。
- 测试发现架构层面的矛盾。
- 需要改变已经批准的架构决议。
- 无法证明持久化或恢复行为正确。
- Git 基线与任务书不一致。
- 工作区存在无法解释的修改。

停止不是失败，而是防止错误架构进入主分支的必要机制。
